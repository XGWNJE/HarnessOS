# AI 编程时代的技术栈选型 Harness

> 写法：目标模式——只描述想要的目标与验收标准，不规定具体做法；做法由模型按情境自决。

提炼自百亿 Token 级 Vibe Coding 实战经验。适用于一切「要让 AI 高频生成、修改、验证代码」的项目。

## 目标：选型服务于反馈闭环，而非生成能力

来源：notes/2026-07-vibe-coding-观察.md；owner-declared（owner 实战选型判断）

判断一项技术是否适合 AI 编程，关键不是「AI 能不能写出它的代码」，而是：

> **生成之后，能否快速检查、验证和修正。**

AI 不擅长「一次写对」，但非常擅长在**反馈足够明确**的情况下持续迭代。技术选型结论应满足以下验收标准：

- **反馈机器可判定**。验收：所选技术的错误信号来自编译器报错、类型检查、测试通过/失败等机器判定，而非依赖人眼判断。
- **反馈足够快**。验收：工具链反馈速度被纳入选型理由；高频迭代场景下反馈慢的选项被显式排除或说明代价。
- **上下文集中**。验收：结构、逻辑、样式能在相对集中的上下文中修改，AI 在文件/范式间的跳转成本被评估过。
- **约束清晰统一**。验收：对 AI 而言，所选方案的约束和规则清晰统一，优先于「无限自由」的方案。
- **生态与语料充足**。验收：所选技术为主流技术，公开代码量与 AI 理解深度被核实过，小众技术只在有明确理由时入选。
- **失败代价匹配约束强度**。验收：错误越接近底层（系统调用、数据、权限），所选技术的约束越强；越接近文件/进程/网络/系统调用，错误代价越高，强类型/编译检查类技术价值越明显。
- **社区真实信号被查过**。验收：选型依据包含 GitHub issue、迁移公告、一线开发者的弃坑记录等一手信号，不以 benchmark 和榜单为主要依据。
- **「轻量替代」的代价被问清**。验收：任何以轻量、小巧为卖点的替代方案，其牺牲项（一致性？生态？可控性？）被明确列出并权衡过。

## 推荐分层栈（Agent 应用，owner 实战结论）

来源：owner-declared（owner 实战选型判断，2026-07 确认）

| 层 | 技术 | 为什么 |
|---|---|---|
| 底层/性能敏感 | **Rust** | 严格类型系统 + 编译器检查提前暴露问题，给 AI 稳定明确的反馈，特别适合「生成—编译—修正」循环快速收敛 |
| 应用逻辑 | **TypeScript** | 静态类型将错误前置；npm 生态的网络效应（连 Deno 都回头兼容 Node/npm）；关注编译性能进展（如原生编译器），补上反馈速度一环 |
| 界面 | **React + Tailwind CSS** | React 组件化把界面拆成边界清晰的结构/状态/交互，公开代码多、AI 理解充分；Tailwind 把样式收敛为可组合、可预测的工具类，AI 不用在组件、样式文件、命名体系间跳转 |
| 运行容器 | **Electron** | Chromium（Agent 观察/操作 Web 的窗口）+ Node.js（连接本地系统/工具的执行层），是天然的 Agent 行动载体；过去的缺点（体积大、资源占用高）在 Agent 时代转化为优势——Agent 恰好需要完整、可编程、跨平台的行动环境 |

组合效果：Agent 可在相对集中的上下文中同时改结构、逻辑与样式，再通过类型检查和视觉反馈迅速验证。这套组合成为主流，不只是因为开发效率高，更因为**天然适配 AI 高频生成—修改—验证的工作方式**。

## 验收红线：选型中的已知坑与不可接受结论

来源：notes/2026-07-vibe-coding-观察.md；owner-declared（Tauri/自编译 Chromium 为 owner 实战调查结论）

以下为已验证的反面结论。验收：选型结论不与以下红线冲突；确要冲突的，显式说明理由并确认 owner 知情。

- **不推荐 Tauri 替代 Electron**。已核实的事实：系统 webview 不确定——不同系统、不同版本表现不一致，webview 有 bug 时无法自行修复只能等系统升级；跨平台一致性差（正是 Electron 用打包 Chromium 换来的东西）；窗口/配置 API 有限、新开授权弹窗与文件下载需自行处理；实战信号：OpenCode 桌面端从 Tauri 迁回 Electron（「WebKit is asssss. Moving to Electron very soon.」）。结论：包体积减小的收益，抵不上稳定性与 Node.js 生态的损失；真正的严重 bug 轮不到你先发现——社区早弃坑了。
- **不推荐自编译 Chromium 跑 Chrome 插件**。已核实的事实：源码+依赖数十 GB，官方要求预留 100GB 磁盘，首次全量构建几十分钟到数小时；三平台需分别维护工具链、补丁、签名、自动更新、回归测试；拿回的是底层能力，并不会自动得到完整 Chrome（Web Store、账号、策略、插件生命周期、权限治理都没有）；最终维护的是一条浏览器厂商级别的内核与发行链路，不是一个应用。
- **成熟生态不被轻言替代**。验收：npm、Chrome 插件体系等成熟生态被当作护城河计入选型权衡；任何替代方案先回答「生态网络效应损失怎么补」。
- **不采信半实现的 API**。验收：兼容性评估对齐「可观察语义」（参数校验、错误作用域、事件投递、生命周期），不以方法名清单为准；方法存在、调用不报错但语义只实现一半的 API 被识别为高风险（会在很远的下游以极难定位的方式失败）。
- **封装层诚实失败**。验收：封装层宁可显式抛错，也不静默降级、不返回「看起来对」的假数据；失败发生在调用点而非下游（来源：notes/2026-07-vibe-coding-观察.md；工作流侧细则见 ai-coding-workflow 第 4 条）。

## 目标：长链路任务靠证据链收敛

来源：notes/2026-07-vibe-coding-观察.md

模型单次生成无法闭环复杂系统任务。验收：复杂系统任务的方案包含一条可反复收敛的证据链，且三要素——**模型能力、工具链、多模态（视觉验证）**——齐备；长链路任务尤其依赖三者协作，缺项被显式指出。

机制（非规定，是无可替代的收敛回路本身）：证据链形态为

```
官方文档 → 上游源码 → 本地实现 → 自动化测试 → 真实环境运行 → 视觉回放 → 发现偏差 → 回到文档和源码
```

这条回路就是「收敛」的物理含义，不是可选的步骤建议；具体每一环用什么工具、走几遍，由模型按情境自决。

## 心智模型速查（owner 判断基线）

来源：notes/2026-07-vibe-coding-观察.md；owner-declared

以下陈述为 owner 的判断基线，选型与评估结论应与之相容：

- 榜单看看就好，真实干活水平只有踩过坑才知道
- 模型强不强是一回事，能不能把它带到正确方向是另一回事——拼的是人的认知和判断力
- Token 消耗量 ≠ 产出价值，它只是「计算与探索消耗」
- 每个程序员都应构建自己的 harness 工程，随大模型一起迭代进化
- AI 时代推翻重写成本大降，兼容历史包袱只会是负债——验收：重写方案动手前，新底座的可验证性（编译/类型/测试等机器可判定反馈）已被确认（细则见 ai-coding-workflow 第 6 条）
