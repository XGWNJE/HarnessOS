# 效果复盘与技能迭代

仅在本轮发现效果差、执行失败、回归或未覆盖机制时使用。授权是维护本技能，不是训练模型、后台持续监控，也不扩大当前项目操作范围。

## 找准需要修正的层级

| 现象 | 先补的证据 | 修正位置 |
|---|---|---|
| 清过一次，但后续仍线性增长 | 重复工作负载、生成入口、保留对象和预算实际覆盖范围 | 项目生成／收尾入口；通用生命周期策略 |
| 目录数稳定，占用或峰值仍异常 | 各资源字节增量、缓存键／版本、归档和临时空间 | 缓存失效、预算或保留方式；不能只看目录数 |
| 预估释放很大，磁盘变化很小 | 逻辑／分配字节、硬链接、其他并发写入、归档成本 | 计量与效果归因；不能把测量误差判为删除失败 |
| 命令、扫描或回收失败 | 原始错误、工具版本、实际路径、链接和权限条件 | 对应工具／平台适配；先缩小复现，不重复整仓操作 |
| 被审批拒绝或仍有未知占用 | 被拒动作及原始理由、当前授权、进程归属 | 调整允许范围或保留该项；不能降低边界以求执行成功 |
| 新项目出现另一种膨胀机制 | 实际写入者、增长触发条件、资源引用和保留约束 | 必要的新策略及诊断能力；不强行归入副本／编译缓存 |

先确认技能是否真的被执行、项目入口是否经过新逻辑。入口未接入、观察窗口不够、正常缓存热身及环境差异，不等于策略已经被证伪；同时不能拿这些理由回避持续增长的证据。

新根因至少说明“谁生成什么、为什么积累、何时可以复用或回收”。单次目录很大、名称相似或一个异常退出码，不足以认定通用根因。与业务持久增长有关时，治理应处理实际容量需求和数据保留约束，不能套用缓存清空。

## 做一次最小、可验证的修正

1. 保存足够定位问题的前后基线、错误和必要现场，确认本轮子进程状态。结果不明时暂停依赖该结果的删除或工作区交接，继续独立可做的工作；不为排错无界复制整个现场。
2. 区分项目实现问题与技能缺口。前者修项目入口／配置；通用决策、误判或工具缺陷修技能。两者都存在时分别修复，不靠只补一句技能文字宣布项目已修好。
3. 修改前读取当前技能及相关引用，核对已有结论和其他修改。选择一个最小改动，不同时改计量口径、目标和策略以掩盖效果差。现有候选不适用时可以增加、替换或合并策略，也可以明确排除不适用场景。
4. 用相同口径、可比输入重跑能揭示问题的最小工作负载。分别核对增长／峰值、耗时、产物正确性、证据与持久数据保护；涉及重试或并发时覆盖该实际失败路径。工具脚本修改须实际运行，并补必要的最小复现；说明文字修改做结构、引用和适用场景检查，不冒称运行效果已验证。
5. 明确改进、无改善、回归或尚未验证。无改善且没有新证据时停止同因重试；只回退本轮无效／有害修改，保留原有有效策略和其他人的修改。未确认的尝试留在当前项目进展中，不能成为通用默认动作。

审批失败与普通工具失败分开处理。可选择更安全、原本允许的工作，但不能换 shell、编码、命令名或技能规则绕过同一个被拒动作。保留不影响主要目标的小项也可能是正确收尾，无需为“清到零”扩大风险。

## 把结论写回正确的位置

先核对技能是否由管理仓库发布。`agent-cleanup` 已由 HarnessOS 纳管，正文事实源为其 `skills/agent-cleanup/`，各 Agent 技能目录是发布副本：先在事实源修订，递增 `metadata.version`，按仓库既有流程校验、发布、提交及同步；不直接修补发布副本。通过当前已知项目或登记信息定位管理仓库，不扫描整机；定位不到事实源时提供最小补丁并说明缺口，不另建技能分叉。

- `SKILL.md`：只保留改变通用决策的触发条件、边界或必要步骤，必要时同步发现描述。
- 已有参考文件：补充适用条件、根因机制、治理方式和验证要点；替换或合并失效、重复的建议。仅在新机制有足够独立细节时增加一个参考文件，并从入口链接。
- `scripts/`：只有重复出现、确定性工具逻辑值得复用时才新增或改脚本。参数化差异，不嵌入用户路径、凭据、项目配额或本机进程号。
- 项目：具体路径、资源预算、例外、原始日志、测量结果和敏感资料留在项目现有维护／证据入口；不复制到全局技能或新建永久案例流水。

策略描述只需说明：适用信号、已证实的生成机制、选用方法与边界、如何验证；推断与实测分开。不把一次成功的节省比例、固定配额或某次失败变成所有项目的硬规则。

写回后运行本机可用的技能结构校验器，检查引用和包内文件；若本轮维护了分发包，同步已有包而非每轮另留副本。技能目录不可写或有无法安全合并的并发修改时，提供最小补丁／明确缺口，不反复复制技能或阻塞独立的项目工作。正常使用后没有新结论时，不修改技能、不生成复盘报告。
