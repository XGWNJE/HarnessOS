# 复用与验证要点

仅阅读当前技术栈需要的部分。这里提供决策点，不指定所有项目必须采用同一种工具或目录结构；实施前核对本机工具版本、已有约定及当前官方文档。

## 选择工作区形态

| 条件 | 优先验证 | 主要代价 |
|---|---|---|
| 同一可信项目、以串行为主、多个构建栈 | 一个稳定路径的受控工作区 | 切换提交时要处理残留；缓存和输出仍需预算 |
| 多任务并行 | 有限工作区池，独立可写输出，共享包下载缓存 | 占用随槽位数增长；不能让任务同时切换同一源码树 |
| 正式门禁要求干净构建、执行来源不可信 | 全新工作区，按信任边界隔离缓存 | 承担必要空间成本，不能为省空间降低隔离或干净构建要求 |
| 主要是旧的成功／失败现场 | 证据归档、完整现场轮换 | 归档不一定能复现；发布／恢复引用需要单独保留 |

复用通常改变的是源码路径、缓存或输出生命周期，不应复用之前“检查成功”的结论。源码、依赖或检查器变化后按现有门禁重新验证。

## Rust／Cargo／Tauri

- 优先验证稳定源码路径下复用同一个 `target`，或 Cargo 支持的 `CARGO_TARGET_DIR`。不同 profile、架构和 flags 会产生必要的不同产物，不把它们全当冗余。
- Tauri、Gradle Rust 插件、组装脚本可能写死 `src-tauri/target/...`；只设置 Cargo 环境变量可能使构建成功、组装读取旧产物。先搜索所有生产者和消费者，再决定是否迁移。
- Cargo 的锁不代替整个验证工作区的互斥。链接目标、外部组装输出及源码切换也要隔离。
- 输入失效由 Cargo 判断；跨路径、构建脚本读取的外部文件和环境输入需要实测。变化的业务行为必须落在新产物中。
- 仅有 `target` 上限还不够：工具链切换、旧 profile 和 incremental 状态可能持续增长。维护闲置缓存时不清正在构建或被运行实例使用的产物。

官方入口：[Cargo 构建缓存](https://doc.rust-lang.org/cargo/reference/build-cache.html)。

## Node／npm

- `npm ci` 会删除现有 `node_modules` 后重装。在固定工作区反复运行它可以限制副本数量，但不等于复用了已安装依赖。
- 先复用包管理器自己的下载缓存。只有安装耗时确实重要时，再考虑跳过未变化的安装：判断至少包含 manifest、锁文件、影响安装的配置／参数、Node／包管理器版本、平台和架构，且仅在安装完整成功后记账。
- 锁文件相同不证明 `node_modules` 未被上轮任务修改。保留校验或按既有可靠入口重新安装；不要仅靠目录存在、mtime 或一张成功标记跳过。
- 多个可写工作区不直接用硬链接或 Junction 共享同一套 `node_modules`；安装、清理和依赖生命周期脚本可能影响另一个任务。
- 单独改变 npm 缓存位置，无法消除每个 checkout 各自展开的依赖目录。

官方入口：[npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。

## Gradle／Android

- 区分下载缓存、项目 `.gradle` 状态、任务构建缓存和各模块 `build` 输出；它们有不同的复用条件。
- 稳定工作区有助于复用已有增量状态；跨工作区缓存依赖任务正确声明输入／输出及可重定位性，不能仅看开启了 `--build-cache`。
- 首次构建、无改动重跑、源码改动和必要配置变更分别观察 `UP-TO-DATE`／`FROM-CACHE`／实际执行，并校验结果。
- 已有正式签名 APK 的保护检查可能拒绝复用验证目录。保留正式包，另设受控的无签名验证输出或只允许覆盖归属明确的验证产物；不能全局放宽保护。
- daemon／worker 的生命周期与槽位互斥一起核对；关闭本轮闲置进程，不误停其他项目共享的进程。

官方入口：[Gradle 构建缓存](https://docs.gradle.org/current/userguide/build_cache.html)。

## .NET／MSBuild

- 全局 NuGet 缓存与每项目 `bin`／`obj` 分开统计。固定工作区通常可复用后者，包缓存本来可能已共享。
- 跨项目统一中间目录时要隔离项目、框架、配置和平台，避免文件覆盖；项目已有默认布局能满足需求时优先保留。
- 编译成功后还要检查新产物及组装输入；删源码后的输出、复制步骤和 SDK／属性变化属于复用验证范围。
- 验证后的 build server／驻留进程按项目既有入口退出，保留仍在使用的共享依赖。

## 证据归档与空间模型

先找检查器、发布、恢复、文档实际引用的文件。归档保留引用闭包，或通过已有机制可靠恢复；复制后在归档位置核对摘要和校验入口。若证明依赖仍存在的原工作树、绝对路径、特定版本检查器或外部资源，不能直接称为可脱离现场的完整证明。

对同一配置粗略建模：

```text
每轮留完整副本：总量 ≈ 持久资产 + 轮次数 × 单轮现场 + 证据
有限工作区池：  总量 ≈ 持久资产 + 槽位数 × 单槽现场 + 共享缓存 + 证据
```

这是趋势模型，不是释放保证。实测应包括持续增长的缓存、保留证据、工具链／依赖版本变化和高峰临时空间。用重复执行后的增长量判断是否收敛，不能只展示一次“清理后”的大小。

方案比较可只用一张表：方式、样本与命令、结束占用／峰值、耗时／命中、变化输入验证、并发／失败验证、改造成本、证据边界。优先采用能解决主要增长、改造少、易验证和恢复的组合。
