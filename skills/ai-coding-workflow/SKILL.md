# AI 编程工作流 Harness

提炼自百亿 Token 级 Vibe Coding 实战观察。关注「怎么组织工作流」，技术栈选型见 ai-stack-harness。

## 1. Token 消耗量不是产出指标

来源：notes/2026-07-vibe-coding-观察.md

实际落到代码的 Token 可能只有 1%~3%，大部分是上下文加载、推理和重写。因此：

- 不要用「今天烧了多少 Token」衡量产出，那只是计算与探索消耗
- 警惕「烧得多 = 干得多」的错觉——大量消耗可能意味着在错误方向上反复重写
- 真正该盯的指标：验证通过的增量（测试、可运行产物、收敛的证据链）

## 2. 榜单不可信，干活水平踩坑才知道

来源：notes/2026-07-vibe-coding-观察.md

- benchmark 和榜单分数与真实任务表现经常脱节；模型选型靠自己在真实任务上的踩坑记录
- 不同模型的强项差异真实存在（如有的创造性方案强但细节有逻辑缺陷，有的长任务推理强）——按任务类型分工，而不是找「万能最强模型」
- 模型换代时旧结论作废，重新踩一遍

## 3. 复杂任务用双模型交叉验证

来源：notes/2026-07-vibe-coding-观察.md

单个模型的盲区是系统性的——它看不出自己的问题。复杂任务用「一个生成 + 另一个 review」：

- 生成模型和 review 模型用不同的，盲区互补
- review 侧重：逻辑缺陷、边界条件、「半实现」（见第 4 条）
- 成本远低于单模型在错误方向上反复迭代的消耗

## 4. 最危险的是「半实现」，封装层要诚实失败

来源：notes/2026-07-vibe-coding-观察.md；语义评估细则见 ai-stack-harness 通用警示

调用不报错但语义只做了一半的代码，会在很远的下游以极难定位的方式爆炸。因此做兼容层、封装层、适配器时：

- 宁可显式抛错（NotImplemented / 明确错误），也不静默降级、不返回「看起来对」的假数据
- 让失败发生在调用点，而不是下游五百行之外
- 审查 AI 生成的封装层时，逐个确认语义完整性，而不是确认「能跑通 demo」

## 5. AI 生成内容 ≠ 知识

来源：notes/2026-07-vibe-coding-观察.md

生成是廉价的，耗时且不可替代的是人的部分：搜集、交叉验证、反复确认。把 AI 输出当「待验证的线索」而不是「结论」，验证环节不能省——省掉验证，你只是把成本转移给了未来的自己。

## 6. Harness > Loop：敢重写，但先确认新底座可验证

来源：notes/2026-07-vibe-coding-观察.md

AI 时代推翻重写的成本大降，兼容历史包袱只会是负债。倾向于重写而非在旧架构上打补丁，但有一个前置条件：**新底座必须能快速验证**（编译、测试、可运行 demo），否则重写只是换一个地方踩坑。
