# AI 编程工作流 Harness

> 写法：目标模式——只描述想要的目标与验收标准，不规定具体做法；做法由模型按情境自决。

提炼自百亿 Token 级 Vibe Coding 实战观察。关注「怎么组织工作流」，技术栈选型见 ai-stack-harness。

## 工作目标

- **产出以验证增量计量，不以 Token 消耗计量**。实际落到代码的 Token 可能只有 1%~3%，大部分是上下文加载、推理和重写。验收：产出评估中不出现「烧了多少 Token」作为产出证据；衡量依据是验证通过的增量（测试、可运行产物、收敛的证据链）；「高消耗、低增量」被识别为可能在错误方向上反复重写，而不是「干得多」。
  来源：已销毁笔记（2026-07-24 vibe coding 观察，内容已提炼完毕，原文销毁于 2026-07-26）

- **模型选型基于真实任务证据，不基于榜单**。事实：benchmark 和榜单分数与真实任务表现经常脱节；不同模型的强项差异真实存在（如有的创造性方案强但细节有逻辑缺陷，有的长任务推理强）。验收：选型依据是自己/团队在真实任务上的踩坑记录；分工按任务类型匹配模型强项，而不是寻找「万能最强模型」；模型换代后旧结论被标记作废，在新模型上重新验证后才再被引用。
  来源：已销毁笔记（内容已提炼完毕，原文销毁于 2026-07-26）

- **复杂任务的缺陷被交叉验证兜住**。单个模型的盲区是系统性的——它看不出自己的问题。验收：复杂任务存在「一个生成 + 另一个 review」的交叉验证环节，且生成模型与 review 模型不同（盲区互补）；review 结论覆盖逻辑缺陷、边界条件、「半实现」（见下一条）；交叉验证成本被视为低于单模型在错误方向上反复迭代的消耗。
  来源：已销毁笔记（内容已提炼完毕，原文销毁于 2026-07-26）

- **封装层诚实失败，不产生「半实现」**。调用不报错但语义只做了一半的代码，会在很远的下游以极难定位的方式爆炸。验收：做兼容层、封装层、适配器时，未实现/不支持的语义显式抛错（NotImplemented / 明确错误），无静默降级、无返回「看起来对」的假数据；失败发生在调用点而不是下游；审查 AI 生成的封装层时语义完整性被逐条确认，而不是只确认「能跑通 demo」。
  来源：已销毁笔记（内容已提炼完毕，原文销毁于 2026-07-26）；语义评估细则见 ai-stack-harness 通用警示

- **AI 输出以「待验证的线索」对待，不以「结论」对待**。生成是廉价的，耗时且不可替代的是人的部分：搜集、交叉验证、反复确认。验收：AI 生成的断言在进入决策、代码或文档前经过验证环节；验证不被省略——省掉验证只是把成本转移给未来的自己。
  来源：已销毁笔记（内容已提炼完毕，原文销毁于 2026-07-26）

- **重写决策以新底座可验证为前置**。AI 时代推翻重写的成本大降，兼容历史包袱只会是负债，倾向重写而非在旧架构上打补丁。验收：推翻重写开始前，新底座已具备快速验证手段（编译、测试、可运行 demo）；不具备时先建立验证手段，而不是直接重写——否则重写只是换一个地方踩坑。
  来源：已销毁笔记（内容已提炼完毕，原文销毁于 2026-07-26）
