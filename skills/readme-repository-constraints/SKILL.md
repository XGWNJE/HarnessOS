# README 模板

为软件、开发工具和数据项目创建或改写 README 时使用本技能。目标是让第一屏先讲清项目身份、用途和开始方式，再按仓库交付方式组织细节。

不用于普通文章、个人说明页、没有代码或数据交付物的仓库，或用户明确指定另一套 README 规范时。

## 先选仓库类型

根据仓库实际交付物选一个主模板；混合仓库按主要使用者的第一任务选择。

| 类型 | 使用资产 | 首屏重点 |
| --- | --- | --- |
| 应用项目 | `assets/application.md` | 给谁用、现在能否试、从何开始 |
| 库与 SDK | `assets/library-sdk.md` | 安装命令与最小可运行调用 |
| 命令行工具 | `assets/cli.md` | 输入、命令、成功时的输出 |
| 数据与机器学习 | `assets/data-ml.md` | 主结果、数据与可复现路径 |

将资产作为结构起点，而不是照抄。替换全部 `{{占位符}}`；没有可靠事实支撑的可选小节直接删掉。「路线规划」是固定章节，没有规划时也必须保留。

## 统一头部

所有仓库类型的 README 头部按以下顺序组成。整个头部居中；从第一个二级标题开始，正文全部左对齐。只在头部使用居中容器，不把正文包进去：

1. **项目图标**：使用仓库已有的正式图标，独占一行并居中；确无正式图标时省略，不生成或借用无关图片。按图标自身留白和目标渲染器调整 `height`，保持原始宽高比。
2. **项目名称**：独占下一行，使用一级标题并居中，不与图标合并。
3. **项目简介**：用一两句话说明项目是什么、用户能用它做什么，居中。
4. **文档导航标签**：用一行 Markdown 链接指向 README 内实际存在的主要章节，以 `·` 分隔，居中；章节删改时同步更新标签和锚点。
5. **项目徽标（徽章 / badges）**：放在导航标签下方并居中，展示已核实的版本、平台、许可证或构建状态等，使用可点击的徽章图片并链接到对应依据或入口；不以纯文字元信息行替代徽标区，不添加无法核实的徽标。

模板用带空行的 `<div align="center">` 包住上述头部内容，并在正文第一个 `##` 前关闭。不要给正文标题、段落、列表或表格设置居中。
安装命令、下载或在线体验入口、实验指标和适用场景等放入对应正文小节。徽标使用可维护的 SVG/PNG 或徽章服务，核对图片与目标链接，提供有含义的替代文本；不使用 AI 生图制作徽标。

## 固定章节：路线规划

所有主模板必须包含 `## 路线规划`，默认放在使用说明之后、贡献与许可之前；头部导航始终保留 `[路线规划](#路线规划)`。项目完全没有涉及未来规划时也不能省略。

- 内容只来自用户明确提出或项目有效文档中仍在考虑的未来方向，不从当前功能、普通问题反馈或个人猜测中推导计划；以具体的预期体验和用户收益建立期待，不编造功能、进度或交付日期。
- 有规划时，使用模板中的提示块与规划表格：提示块突出「接下来，值得期待」，明确这些是预期方向，不保证开发或交付；表格展示方向、用户能期待什么和当前状态。用简短醒目的方向名与准确的状态标签增强层次，正文保持左对齐，不依赖装饰图片或自定义 CSS。
- 状态可采用「💭 构想中」「🔎 评估中」「🛠️ 开发中」，仅按已确认事实选择；未说明排期时写「未排期」，不把愿望写成开发承诺。不要用已完成事项填充未来规划；已交付内容应归入当前功能。
- 没有任何规划依据时，保留章节，正文使用引用块 `> **暂无。** 当前没有已公布的未来规划。`，删除规划表格和有规划时的提示块；不要留下空表或占位符，也不要暗示即将发布计划。
- 后续更新时核对规划是否仍有效：移除已放弃的方向，已交付的内容移入当前功能；全部清空后恢复「暂无」，始终保留标题与导航。

## 不可省略的约束

- 先核对仓库内已有的名称、正式图标、运行命令、许可证、版本、链接和截图；不猜测、不编造指标、徽章、路线图、安装命令或在线地址。
- 用户要求重构或全面刷新 README 时，从当前项目的代码、配置、测试、发布记录和有效文档重新梳理内容与结构；旧 README 只作待核对的线索，不沿用其章节、措辞或未经证实的结论。
- 用尽可能直白的话说明用户能做什么、怎样操作、会得到什么；只有准确表达确实需要时才使用术语，并在首次出现时用白话解释。
- 逐项核对 README 中的事实是否仍与项目现状一致，尤其是功能、平台、目录、命令、依赖版本、配置、发布状态和外部链接。需要时查实时权威来源，并区分已验证事实与待确认信息。
- 重新制作演示界面或截图属于耗时的独立工作；除非用户要求，不把它作为刷新 README 的默认步骤。仍须核对已有截图或演示的路径与内容是否适用；无法确认时标明，不用旧画面暗示当前功能。
- 确实需要新架构图、流程图或数据流图来解释项目时，使用现有 `archify` 技能，并以项目事实为依据；不要为了装饰而加图。
- 不生成或添加氛围图、装饰性横幅、伪产品图或带文字的生图。截图、架构图和流程图只在能解释具体功能、接口或操作时使用。
- 导航、命令和详细指标使用 Markdown/HTML 文本，不烘焙进图片；头部徽标可用图片显示已核实的版本、平台、许可证和状态等信息，不受此限制。
- 开场使用具体、可验证的说法：用户做什么、输入什么、得到什么。避免“赋能”“一站式”“极致体验”“提升效率”等没有证据的营销语。
- 代码块和命令必须与仓库现状相符，且要说明必要前提、预期结果或失败提示。
- README 面向使用者；贡献、开发、发布和架构细节放在使用路径之后，或链接到专门文档。

## 写作与验证

1. 从仓库文件和已有文档提取事实，并选定一个模板。
2. 让第一屏可在一分钟内回答：这是什么、适合谁、怎么开始。
3. 当前功能、平台和流程仅写项目确实支持的内容；未来方向集中放在「路线规划」并标明不保证交付。对于限制或不适合的使用场景，直接说明。
4. 提交前检查：头部顺序符合「项目图标单独一行 → 项目名称单独一行 → 项目简介 → 文档导航标签 → 项目徽标」，头部全部居中且正文左对齐，图片（含徽标）和目标链接有效、导航锚点与实际章节一致、命令没有明显矛盾、占位符已经清空。有正式图标时，在目标 README 渲染器中检查图标、标题和其余头部内容的居中效果，以及正文的左对齐；无法预览时明确标为未验证。
5. 检查「路线规划」标题与导航始终存在；有规划时提示块、用户收益和状态齐全，无规划时明确写「暂无」，没有虚构承诺、已完成事项或遗留占位符。

如果缺少关键信息，保留简短待补标记或询问用户；不要用看似完整的虚构内容填满 README。未来规划没有依据时按「暂无」处理。
